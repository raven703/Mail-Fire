# Единый интерфейс редактирования — аудит frontend

Основа: `master` 8c3f1d2. Ветка `feature/consistent-edit-dialogs-20261119`.
Цель: создание и изменение бизнес-объектов выполняется во **всплывающих
модальных окнах одного стиля**, а не в разрозненных формах внизу страницы.

## Общий контракт

Компонент `frontend/src/EditorDialog.tsx` + стили
`frontend/src/editor-dialog.css`. Для любой формы редактирования:

- Настоящий нативный HTML `<dialog>` с `showModal()`, React portal в body.
- Одинаковые заголовок/подзаголовок, крестик, скроллируемое содержимое,
  прикреплённые кнопки **Отмена**/**Сохранить**.
- Escape, крестик или «Отмена» закрывают **без API-запроса**.
- Клик за пределами не закрывает диалог.
- Фокус переводится в первое доступное поле и восстанавливается при закрытии.
- Нативная валидация form `required`, `min`, `max`, type; ошибки API внутри окна.
- Пока идёт отправка: закрытие и повторное сохранение блокируются.
- Светлая/тёмная темы используют `--card`, `--border`, `--text`,
  `--accent`, `--muted` без новых цветов; стили кнопок/checkbox/select из
  `controls.css` не меняются.
- Один внутренний скролл, без двойного скролла в редакторе политик;
  1440px и 375px, доступность табуляцией.

## Аудит разделов

| Раздел | Действие | Новое поведение |
|---|---|---|
| DLP-политики | Создать / редактировать | Общий EditorDialog (заменён старый отдельный shell) |
| Категории данных | Создать / «Правила и настройки» | **EditorDialog**; форма не расширяет страницу |
| Выбор категорий в политике/ML | «Новая категория» | Вложенный EditorDialog поверх родительского |
| Настройки → Пользователи | Добавить / открыть строку пользователя | EditorDialog |
| Настройки → SIEM | Редактировать назначения | EditorDialog |
| Настройки → Хранение | Изменить сроки | EditorDialog |
| ML → Наборы данных | Импорт CSV/JSONL | EditorDialog |
| ML → Наборы данных | Изменить/подтвердить метки примера | EditorDialog |
| ML → Разметка | Добавить обучающий пример | EditorDialog |
| ML → Обучение | Запустить новый job обучения | EditorDialog |
| Инцидент | Назначить аналитика | EditorDialog |
| Инцидент | Изменить решение/комментарий | EditorDialog |
| Инцидент → Обучение на решении | Добавить пример | EditorDialog |
| Эталонные документы | Добавить/загрузить эталон | EditorDialog |

**По замыслу остаются без модалок:** поисковые фильтры и вкладки,
переключатели мгновенной активации, смена темы, навигация, импорт
входящих EML (загрузка, а не изменение настроек). Для необратимых
действий (архивирование, удаление, очистка) пока используются существующие
браузерные подтверждения; задача унификации редакторов не изменяет
опасные действия и их семантику. Детекторы включаются переключателем,
без отдельной формы конфигурации.

**Чтение без редактирования:** подробные сведения о почте, инцидентах,
эталонах и метриках остаются в контексте страницы, их не обязательно
переносить в форму.

**Риск совместимости:** после объединения PR #6 (backend) возможен
Git-merge без прямых пересечений, поскольку данный PR меняет только
frontend и smoke-скрипты.

## Обязательные проверки агента

В этой сессии изменения внесены непосредственно в GitHub. Нет доступа к
работающему localhost пользователя, отсутствует доступ к его Docker/Vite
окружению — **runtime проверки не выполнялись**. Это не готовый релиз.

1. `cd frontend && npm ci && npm run build`. Сборка обязательно должна
   пройти (`tsc --noEmit` и Vite).
2. Запустить `node scripts/edit_dialogs_smoke.cjs` с установленным
   Playwright и доступным локальным стендом. Тест открывает редакторы и
   закрывает их **без сохранения**; отслеживает неожиданные API-записи.
3. Проверить `node scripts/category_picker_smoke.cjs`,
   `node scripts/policy_modal_smoke.cjs`,
   `node scripts/security_overview_smoke.cjs`,
   `node scripts/ui_smoke.cjs`. Скрипты устаревали после PR #5; обновлены
   селекторы под текущую разметку, оставшиеся несоответствия исправить.
4. Отдельно на **тестовом** стенде сохранить и отредактировать одну
   синтетическую категорию (keywords/regex/reference/ML), одну политику,
   пользователя, настройки SIEM, учебный пример и пример датасета,
   затем перезагрузить страницу и подтвердить, что значения сохранились.
   Не трогать production данные.
5. Проверить вложенные диалоги: создание категории из политики/разметки.
   Escape должен закрыть только верхний слой, состояние родителя
   сохраняется. При выполнении Save — только целевой POST/PUT, а не
   отправка родительской формы.
6. Проверить `role=dialog`, корректную валидацию, focus-trap браузера,
   клавиатуру (Esc/Enter/Tab/Space), длинные тексты и 375px.
7. Сделать 4 скриншота: категория edit (light/dark, desktop/mobile),
   плюс policy/ML/Accounts по одному. Внести необходимые исправления.

**Не объединять с master до зелёного TypeScript/Vite и браузерного
smoke-теста.** Не нажимать реальные удаления, очистки и переобучение
на рабочей БД. Не добавлять непроверенные фиктивные UI-контролы.
