# Версионируемые DLP-политики и категории — правило как код

## Идея

Файл `config/rulepacks/base_ru.json` — стартовый **редактируемый агентом**
набор российских DLP-категорий и соответствующих политик. Вместо ручного
изменения PostgreSQL можно править JSON, проверять diff через Git и применять
его на тестовом стенде после одобрения администратора.

**Никакой синхронизации при старте**: `bootstrap` не загружает файлы.
Изменение JSON в Git **само по себе не меняет действующие политики**.
Все базовые политики имеют `enabled:false`, чтобы избежать внезапного
уведомления SIEM и множества ложных инцидентов. Категории включены, но
без активной политики сами по себе не создают инцидент.

## Конфигурация

Схема v1:

```json
{
  "schema_version": 1,
  "name": "my-org-v1",
  "description": "Назначение набора",
  "categories": [
    {
      "id": "pack-my-category",
      "name": "Контроль тестовых кодов",
      "group_name": "Мои категории",
      "description": "Описание",
      "active": true,
      "match_mode": "any",
      "rules": [{
        "kind": "keywords",
        "title": "Поиск фразы",
        "enabled": true,
        "risk": 60,
        "priority": 100,
        "phrases": ["внутренний тестовый код"]
      }]
    }
  ],
  "policies": [{
    "name": "Моя политика",
    "enabled": false,
    "shadow": false,
    "priority": 100,
    "min_risk": 40,
    "min_count": 1,
    "category_match": "any",
    "categories": ["pack-my-category"],
    "direction": [],
    "senders": []
  }]
}
```

Поддерживаются **те же** типы правил, что и в UI:
`keywords`, `regex` (ограниченный синтаксис), `reference` (только
существующие локальные эталоны), `ml` (только опубликованная модель).
Наличие правила `ml` **не обучает** модель. Политика может ссылаться
на встроенные категории (например `SECRET`), если они доступны в БД.
Системные категории не переопределяются.

Новые управляемые ID должны быть `pack-...` (ASCII lowercase);
экспортированные пользовательские категории `custom-<uuid>` тоже
принимаются при обратном импорте. **Не изменяйте ID после создания**.
Политики идентифицируются по названию; для стабильных обновлений не
переименовывайте политику в JSON, иначе будет создана новая.

## Управление через запущенный контейнер

Из корня проекта на хосте, где работает Docker:

1. **Предпросмотр, без записи в БД:**

```bash
docker compose exec -T api python -m app.rulepacks_cli preview - < config/rulepacks/base_ru.json
```

2. **Создать недостающие категории/политики (с записью аудита):**

```bash
docker compose exec -T api python -m app.rulepacks_cli apply - --actor admin < config/rulepacks/base_ru.json
```

3. **После изменения JSON посмотреть, что перезапишется:**

```bash
docker compose exec -T api python -m app.rulepacks_cli preview - --update-existing < config/rulepacks/base_ru.json
```

4. **Только после просмотра и резервного копирования БД — обновить
существующие объекты:**

```bash
docker compose exec -T api python -m app.rulepacks_cli apply - --actor admin --update-existing < config/rulepacks/base_ru.json
```

5. **Экспорт в файл на хосте (не в контейнере):**

```bash
docker compose exec -T api python -m app.rulepacks_cli export --output - > mailfire-export.json
```

Операция `export` включает пользовательские категории `custom-...`
и `pack-...`, а также политики, которые ссылаются только на такие
категории и/или встроенные категории. Не экспортируются письма, датасеты,
ML-веса, учетные записи, токены и эталонные документы.
**Содержимое Regex/словарей тоже может быть чувствительным** — храните
экспорты в приватном репозитории, проверяйте перед коммитом.

При запуске `preview` и `apply` после `pull` **сначала пересоберите
API image**, чтобы новая команда `app.rulepacks_cli` была доступна.
Просто изменить JSON без обновления CLI можно, если установленная версия
поддерживает его схему.

Текущий инструмент: dry-run, транзакционное создание/обновление,
журнал аудита, защита системных категорий, проверка ссылок.
**Нет удаления объектов из БД при отсутствии их в файле.**
По умолчанию существующие записи пропускаются — только
`--update-existing` допускает перезапись. Это важно, если кто-то
изменил категорию вручную через UI: импорт может заменить её правила
при указанном флаге.

## Категории из базового пакета

- Угрозы взрывов и опасных предметов.
- Угрозы физического насилия.
- Вымогательство и шантаж.
- Непубличные финансовые прогнозы.
- Внутренние служебные документы.
- Контекст передачи учётных данных.

Правила обнаруживают **явные ключевые формулировки**, но не умеют
достоверно распознавать намерение, цитату, сарказм, жалобу пострадавшего
или угроза vs новость. **Не следует считать совпадение доказательством
угрозы или виновности**; любые предупреждения требуют ручной оценки.
Особенно важно тестировать отрицательные случаи (цитата, сообщение о
предотвращении, пересказ статьи) и не отправлять их автоматически во
внешние системы до калибровки.

Для **смыслового анализа угроз** потребуется отдельная обученная
категориальная ML-модель с разнообразной размеченной русскоязычной
выборкой и отдельным тестовым корпусом; SetFit/RuBERT могут
использоваться через существующие механизмы `ml`.

## Разрешённая последовательность для агента

1. Меняет `config/rulepacks/base_ru.json` либо создаёт новый файл
   `config/rulepacks/org-*.json`.
2. Делает code review и анализ FP/FN на синтетических фразах.
3. Запускает `preview`, фиксирует отчёт изменений.
4. **Только после подтверждения администратора** вызывает `apply`.
5. Проверяет, что категории доступны в UI; включает конкретную политику
   вручную в тестовом стенде и импортирует синтетические EML.
6. Не использует `--update-existing` при наличии неучтённых
   изменений пользователей без сравнения актуального экспорта и Git.
7. Для rollback — сначала экспорт активных настроек, потом ручное
   восстановление предыдущей версии (CLI не удаляет лишние объекты).

**Это конфигурационный механизм, не универсальный DLP-движок.**
Слова, которые точно обнаруживают преднамеренные угрозы, без учёта
контекста и ML выделить невозможно.

## Дополнения при приёмке PR #8

В разделах «Категории данных» и «DLP-политики» администратору доступны
«Экспортировать JSON» и «Импортировать JSON». Импорт требует предварительного
просмотра; apply повторно проверяет файл. Лимит — 1 МиБ, CSRF и роль admin
обязательны. Экспорт и применение фиксируются в аудите.

Импорт никогда не включает политики: после проверки включайте их отдельно.
Обновление существующего элемента разрешено только набору с тем же `name`,
зафиксированным в аудите первоначального импорта. Ручные и чужие элементы
обновлять нельзя; без флага обновления они пропускаются. Имя набора —
операторский идентификатор происхождения, не криптографическая подпись.
Дополнительные поля условий существующей политики сохраняются.

Базовые keyword-категории **не понимают контекст цитирования и отрицания**:
цитата «я тебя убью» в статье тоже создаёт находку. Это известный false positive,
а не доказательство угрозы автора. Политики оставлены выключенными именно
для ручной проверки контекста. Не добавляйте глобальные исключения вроде
«цитата»: ими можно замаскировать реальную угрозу в том же тексте.
