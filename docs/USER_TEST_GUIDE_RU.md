# Mail-Fire — практическая инструкция по испытаниям (локальный стенд)

**Версия основы:** исходники `master` на коммите `8c3f1d2` (после PR #4).
Этот документ — эксплуатационные сценарии для администратора и аналитика,
**не** подтверждение безопасности промышленного внедрения.

## 0. Что уже проверено и чего НЕ означает health=ok

Со слов оператора, развёрнуты PostgreSQL (Alembic 0006), API, parser и
neural-worker, общий исходный каталог модели: `/opt/local-ml/rubert`.
API `/api/health` отвечает `{"status":"ok"}`.

Это подтверждает доступность API/БД, но **не доказывает** прохождение
train → save → publish → infer на реальных весах, качество классификации,
отсутствие сетевых запросов и надёжность отдельных детекторов. OCR, ClamAV
и другие компоненты требуют самостоятельных проверок.

Не используйте реальные паспорта, ключи, служебные письма и документы.
Применяйте только вымышленные тестовые данные и локальный стенд. Не
подключайте настоящий BCC/SMTP-поток на этом этапе.

## 1. Права пользователей

- **Администратор:** создаёт/редактирует категории и политики; загружает
  датасеты, запускает обучение, публикует версии моделей, управляет системой.
  Для чтения исходного текста датасетов нужен отдельный флаг доступа к
  оригиналам/содержимому.
- **Аналитик** с доступом к оригиналам: просматривает тексты, проверяет
  разметку импортированных датасетов, расследует инциденты, корректирует
  примеры и решения. Не может самостоятельно публиковать модели.
- **Наблюдатель:** просмотр доступных сводок, без просмотра оригинального
  содержимого при отсутствии отдельного разрешения, без управления
  политиками/обучением.

Интерфейс: `http://localhost:8080` на том же компьютере со стендом;
`admin` и пароль, выбранный при развёртывании. HTTP/небезопасные cookies
допустимы только на loopback-стенде, не открывайте порт извне.

## 2. Быстрый запуск проверки обычных писем

1. Откройте **DLP-политики**. Уже может существовать системная политика
   «Высокий риск — проверка аналитиком» с порогом **60**. Для чистой
   проверки лучше временно отключить её либо учитывать дополнительные
   инциденты, которые она создаёт.
2. Создайте политику «ТЕСТ — секреты в письмах»:
   - включена; **теневой режим выключен**;
   - категории: `Секреты / SECRET` (ориентируйтесь на код `SECRET`);
   - объединение: **Любая (ИЛИ)**;
   - минимальный риск **40**, минимум срабатываний **1**;
   - направления — **не выбраны** (это означает все направления);
   - отправители — пусто (любой).
3. Сохраните и перейдите в **Импорт писем**.
4. Подготовьте UTF-8 EML (пример ниже) и загрузите его через поле
   загрузки. Можно альтернативно положить файл в `data/import/inbox/`,
   дождаться стабильного размера/mtime и автоматического сканирования.
5. Проверьте **Почтовые сообщения**: письмо появилось, статус
   `ANALYZED` или `PARTIAL` (если отдельный компонент недоступен).
   `PARTIAL` не означает «чисто».
6. Проверьте **Инциденты**, период **Последние 24 часа**, сбросьте фильтры
   при необходимости, найдите письмо по теме. Откройте инцидент:
   ожидается категория `SECRET`, совпавшее правило, выдержка и
   числовой риск. Если политика не сработала, проверьте её порог,
   направление, теневой режим, состояние детекторов и категорий.
7. Вернитесь в **Обзор безопасности**: сводка должна учитывать инцидент
   за выбранный период. `UNKNOWN` в состоянии сервисов не равно
   `ERROR`.

**EML №1 — секрет:** создайте файл `synthetic-secret-001.eml`:

```eml
From: worker@example.test
To: outsider@external.test
Subject: TEST-001 fictional access token
Message-ID: <mailfire-test-001@example.test>
MIME-Version: 1.0
Content-Type: text/plain; charset=UTF-8
Content-Transfer-Encoding: 8bit

Это синтетическое письмо. api_key=synthetic_never_valid_token_001
Данные вымышленные, ключ не работает.
```

Ожидаемый встроенный детектор: `SECRET` с риском **85**; при порогах
HIGH >=70 это создаёт инцидент HIGH. Состав других находок
может отличаться в зависимости от активных движков/категорий.

**EML №2 — секретов нет:** аналогичное письмо с другим
`Message-ID` и темой, но телом «Публичное расписание встреч. Только
синтетические сведения». При изолированной политике SECRET не должно
быть инцидента по этой политике.

**EML №3 — коммерческая тайна:** тело «Коммерческая тайна. Синтетический
внутренний план выручки». Ожидаемый встроенный `CONFIDENTIAL` —
риск **65**. Для него создайте отдельную тестовую политику,
содержащую категорию `CONFIDENTIAL`, либо настройте категорию как вторую
в тестовой политике с режимом ИЛИ. Не путайте ML с Regex: этот тест
проверяет **правила**.

**Важно о направлении:** если `INTERNAL_DOMAINS` не содержит
`example.test`, направление может стать `UNKNOWN`. Для первого
теста оставьте фильтр направления пустым. Если нужно проверить OUTBOUND,
задайте тестовый внутренний домен в конфигурации и перезапустите только
необходимые сервисы в отдельном стенде.

В `scripts/generate_samples.py` уже есть генератор 10 синтетических EML:
`uv run python scripts/generate_samples.py --count 10`.
Он пишет в `data/import/inbox`, все примеры содержат один и тот же
секрет/коммерческую тайну; это **smoke-тест импорта**, не измерение качества.

## 3. Как настраивать категории и политики

### Категория — ЧТО искать

**Категории данных → Категория**. Для новой категории задайте название,
группу и как объединять её правила: **Любое (ИЛИ)** или **Все (И)**.
Внутри категории можно добавить несколько правил:

- `Ключевые слова`: список фраз; срабатывает при нахождении фразы.
- `Безопасный Regex`: ограниченный синтаксис, без сложных конструкций;
  подходит для известных кодов и номеров документов.
- `Эталонные документы`: сравнение текста с загруженным эталоном по
  отпечаткам/семантическому сходству при настройке правила.
- `ML-модель`: классификация текста по локальной опубликованной модели
  данной категории; укажите минимальную уверенность, например 0.70.

Для каждого правила задаётся собственный **риск 0–100**. Для теста
можно создать «ТЕСТ — Финансовый прогноз», правило по фразе
«плановая выручка», риск 70. Для ML-теста создайте категорию с
**правилом типа ML**, например риск 70 и `min_confidence=0.70`.

### Политика — КОГДА создавать инцидент

**DLP-политики → Новая политика**:
- выбрать одну или несколько категорий;
- `Любая (ИЛИ)`: достаточно находок в любой выбранной категории;
- `Все (И)`: нужна минимум одна подходящая находка **в каждой**
  выбранной категории;
- `Минимальный риск`: применяется **к каждому отдельному признаку**;
- `Минимум срабатываний`: количество находок, удовлетворяющих фильтрам;
- `Приоритет`: порядок проверки, **не исключает** остальные политики;
- дополнительные фильтры: направление и точные адреса отправителей;
- `Теневой режим`: для этой политики **инцидент не создаётся**.

На одно событие доставки письма может быть создан один инцидент
**на каждую сработавшую политику**. Поэтому в тестовом стенде отключите
лишние политики для однозначного результата.

**Критичность:** вычисляется из **максимального риска** подходящих находок:
LOW 0–39, MEDIUM 40–69, HIGH 70–100. Количество совпадений пока не
повышает риск автоматически; накопительный риск не реализован.

## 4. Как подготовить синтетический датасет для ML

Для одного пробного обучаемого класса подготовьте **60–100 разных**
сообщений: не меньше 30 положительных и 30 отрицательных. Текущий
минимум кода — 30 уникальных подтверждённых текстов в целом, как минимум
6 положительных и 6 отрицательных, но минимальный корпус может не пройти
стратифицированное разделение train/validation/test или метрики.

Размеченный JSONL (UTF-8), **один объект на строку**:

```jsonl
{"text":"Синтетический финансовый план: плановая выручка следующего квартала и внутренний бюджет отдела.","labels":["ТЕСТ — Финансовый прогноз"]}
{"text":"Публичное приглашение на выставку технологий с расписанием докладов и адресом стенда.","labels":[]}
{"text":"Черновая оценка затрат и плановой маржи для условного проекта Альфа в будущем квартале.","labels":["ТЕСТ — Финансовый прогноз"]}
{"text":"Открытое приглашение на вебинар для всех желающих по теме программирования и дизайна.","labels":[]}
```

Это демонстрация формата, **не готовый набор из 60 примеров**. Каждая
строка должна быть **уникальной по содержанию**; простая замена номера
не считается хорошим разнообразием. `labels: []` автоматически
превращается в отрицательную метку `NORMAL`.

Можно использовать внешнюю LLM **вне Mail-Fire**, но отправляйте ей
только вымышленные данные. Пример запроса:

> Сгенерируй 80 разнообразных **полностью синтетических русскоязычных**
> текстов электронных писем для тестирования классификатора. 40
> положительных примеров внутреннего финансового прогноза компании
> (маржинальность, непубличная выручка, бюджеты и цены), 40 отрицательных
> (публичные мероприятия, общие новости, публичный маркетинг, публичная
> статистика, нейтральные рабочие письма). Перемешай порядок. Используй
> вымышленные названия, не используй реальные персональные данные, ключи
> или секреты. Верни ТОЛЬКО UTF-8 JSONL, без Markdown, строго поля
> `text` (30–500 символов) и `labels` (массив), где для положительных
> `["ТЕСТ — Финансовый прогноз"]`, для отрицательных `[]`.
> Избегай одинаковых шаблонов, повторяющихся вводных и искусственных
> маркеров «положительный/отрицательный». Не копируй реальные документы.

Для независимой проверки попросите **вторую партию** из 20
ранее не использованных примеров, **не загружайте её в обучающий датасет**.
Не доверяйте меткам LLM без проверки человеком.

## 5. Импорт, разметка, обучение, публикация

1. **ML-модели и обучение → Наборы данных**. Администратор с правом
   просмотра оригиналов вводит имя, источник (`external-llm`), выбирает
   `.jsonl` или `.csv` (UTF-8, максимум 12 МиБ, 5000 строк).
2. Если внешняя метка совпадает с названием/ID категории, mapping
   необязателен; иначе передайте JSON отображения
   `{"finance":"custom-<id категории>"}`, подставив настоящий ID.
3. Нажмите **Загрузить на проверку**. Все строки сначала
   `approved=false`. Статус датасета `REVIEW`.
4. Откройте **Проверить примеры**, прочитайте текст и метки,
   при необходимости **Изменить метки** → **Подтвердить**. Каждая
   строка требует подтверждения. После подтверждения всех строк
   датасет становится `READY`; обучаться могут только подтверждённые
   примеры. Набор может обучаться и в статусе REVIEW, если 30+
   примеров уже подтверждены.
5. Откройте **Обучение**, задайте название версии и выберите:
   - `TF-IDF`: базовая многометочная модель по всем категориям,
     обучается на утверждённых примерах, не требует RuBERT.
   - `SetFit`: отдельная бинарная модель для выбранной категории.
   - `RuBERT-tiny2`: другая бинарная модель для выбранной категории.
6. Выберите датасет, категорию для SetFit/RuBERT, `min_f1=0.70`,
   нажмите **Запустить обучение**. Статус отслеживается в
   **Очереди обработки**. Не путайте постановку в очередь с успехом.
7. После `DONE` откройте **Модели**, изучите **Метрики**
   (precision, recall, F1, support по validation/test). Если модель
   `eligible`, администратор может нажать **Опубликовать / откатить**.
   Если F1 не пройден или job `DEAD`, сначала изучите ошибки,
   исправьте корпус или окружение, не публикуйте слабую модель.
8. Для одной категории активна **только одна специализированная**
   модель SetFit **или** RuBERT; публикация заменяет прежнюю
   специализированную версию **этой же категории**. Общая TF-IDF
   может быть активна параллельно.
9. В созданной ранее категории должно быть **включено правило ML**
   с `min_confidence`, а DLP-политика должна включать эту категорию,
   иначе даже успешное `/api/ml/infer` не создаст инцидент.
10. Импортируйте **отдельные контрольные EML** с новыми текстами,
    не входившими в обучение. Ожидайте срабатывание категории и
    инцидент при выполнении порогов. Проверяйте ложные срабатывания
    на отрицательных письмах. Проверяйте **доказательства**, а не только
    общий счётчик.

### Веса модели и офлайн-режим

Наличие neural-worker и каталога `/opt/local-ml/rubert` показывает
конфигурацию, а **не доказывает успешное обучение**. Один
`cointegrated/rubert-tiny2` может быть базой для двух методов. SetFit
потребует корректные SentenceTransformer `modules.json` и pooling
метаданные в локальном snapshot. Обученные артефакты будут разными.

При проверке без интернета сначала однократно подготовьте веса
и зависимости в доверенной среде, затем отключите внешние сети и
выполните train/infer. Переменные `HF_HUB_OFFLINE=1` и
`TRANSFORMERS_OFFLINE=1` сами по себе не доказывают отсутствие
сетевых обращений — требуется сетевой контроль контейнера.

## 6. Результаты, которые должен записать испытатель

| Сценарий | Ожидаемое поведение |
|---|---|
| Письмо с вымышленным api_key | SECRET, риск 85, HIGH при тестовой политике |
| Письмо без секретов | Нет инцидента по политике SECRET |
| «Коммерческая тайна» | CONFIDENTIAL, риск 65 при отдельной политике |
| Теневой режим | Никаких новых инцидентов этой политики |
| Политика ALL | Инцидент только при наличии всех категорий |
| Загрузка JSONL | Статус REVIEW, примеры НЕ подтверждены |
| Подтверждение аналитиком | Изменение approved и аудит |
| SetFit/RuBERT train | JOB DONE либо явная ошибка (не считать успехом без реального inference) |
| Публикация модели | Только eligible; прежняя версия той же категории неактивна |
| Новые контрольные письма | Распознавание совпадений и отсутствие ожидаемых ложных тревог |

Рекомендуется записывать: файл письма, ожидаемые находки,
фактические находки, созданную политику, риск, состояние job,
версию модели, случаи FP/FN. `/api/health` и `64 passed` не
заменяют функциональной приёмки.

## 7. Важные текущие ограничения

- Это **пассивный** мониторинг копий писем: созданный инцидент
  не блокирует отправку, не изымает сообщение у адресата.
- Семантическое сходство и ML-вероятность — признаки, а не доказательство
  утечки. Для ПДн могут требоваться отдельные Regex/NER.
- Риск инцидента пока `max(finding.risk)`, не сумма и не
  накопительная модель риска.
- Старые инциденты не удаляются автоматически при отключении/смене
  политики; сравнивайте события с подходящей датой/версией.
- Исходные тексты и датасеты сохраняются в PostgreSQL; контроль хранения
  обучающих текстов требует дополнительной проверки.
- Если у письма уже был создан инцидент до семантического прохода,
  исходный код не обновлял его `risk/findings` при втором проходе.
  В PR #6 повторная оценка обновляет `risk/findings`, сохраняя статус,
  исполнителя и комментарии без повторного уведомления. Старые инциденты
  обновляются при повторной оценке, а не автоматически при обновлении приложения.
- После повторного анализа уже отправленная внешняя SIEM-нотификация
  не исправляется задним числом; может содержать первоначальный риск.
- Не считать готовым промышленный BCC/SMTP/враждебные вложения без
  дополнительной проверки изоляции и ограничений.
