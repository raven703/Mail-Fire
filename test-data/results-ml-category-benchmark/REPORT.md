Для 750 писем найдено 730 различных текстов, 20 точных повторов и **0 конфликтов меток** у точных повторов. Внутри 128 групп `корпус:scenario` также нет конфликтов меток. ## Проверка многометочности и штатных путей

`app.ml.train` обучает глобальный `OneVsRestClassifier(LogisticRegression)` с `MultiLabelBinarizer`, поэтому TF-IDF поддерживает несколько категорий для одного письма. `app.ml_engines.train_binary` обучает независимые бинарные SetFit/RuBERT модели по категории; `app.ml_runtime.infer_models` объединяет их предсказания. Для сравнения нейронных движков понадобились бы 12 отдельных моделей каждого типа. Производственный код и БД не менялись.

Штатный TF-IDF сначала объединяет только **одинаковые тексты после нормализации пробелов и регистра** через `group_hash`, затем случайно перемешивает 730 хешей с `np.random.default_rng(42)` и режет их 60/20/20. Аудит точно воспроизводит эту процедуру: train 438, validation 146, test 146. **79 из 128 сценарных групп** попали в две или три части. Порог для каждой категории штатно выбирается на загрязнённой validation и дополнительно оценивается на загрязнённом test.

Штатный SetFit/RuBERT путь `_binary_data` использует `train_test_split(..., stratify=y)` только по бинарной метке и тоже не принимает идентификатор смысловой группы. При выполнении этой штатной функции для каждой категории **75–79 из 128 сценариев** пересекают части train/validation/test. `train_binary` затем подбирает порог на validation. Таким образом, проблема относится ко всем трём движкам. Полные счётчики по 12 категориям сохранены в `audit.json`.

Отбор одного письма на сценарий уменьшил бы набор до 128 текстов, отбросил 622 наблюдения и всё ещё не гарантировал бы разделение шаблонов между разными именами сценариев. При детерминированном выборе последнего письма в каждом сценарии штатный TF-IDF split оставляет категорию `pricing` без положительных примеров на validation и отвергается собственной проверкой. Такой отбор не служит корректной заменой групповому split.

До этого подбор порогов и итоговая проверка на B-500 остаются невыполненными. Эта ветка не содержит изменений архитектуры, производственного кода или правил RU3/RU4.
