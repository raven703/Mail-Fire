# Horizon: комбинированное обнаружение и интеграция

## Статус и ограничения интерпретации

Экспериментальный, выключенный по умолчанию дополнительный метод. Никакого автоматического блокирования или изменения рабочего развёртывания. Ветка от main после слияния PR36; PR28/37/38 не объединялись.
**Все комбинации и рекомендации подобраны на ранее использованном B-500. Это исследовательский анализ, НЕ независимая проверка качества. Нужен новый человечески проверенный корпус.**
B-500: 500 писем × 12 категорий = 6000 решений; 300 положительных решений, 260 безопасных писем. Метрики относятся к пользовательским RU2/RU3/RU4 категориям, не к нативным PII/антивирусным детекторам.

## Сопоставление источников

Проверены точные множества 500 ID, отсутствие дублей, все 12 category ID и идентичность expected-меток каждого письма для семи вариантов предсказаний. Проверены SHA256 текстов Horizon против observations; хэши manifest/observations совпадают с входами исторического ML experiment. Старые messages.json не содержат собственных per-message text SHA: для них проверена цепочка происхождения, а не выдуманная независимая повторная проверка текста.
Исходные commit и SHA256 файлов — `provenance.json`. Сохранённые предсказания берутся из PR38 (`d846b91`), ML category benchmark (`19cdc936f342e2b7330fb07e1b5815a8dd604bcd`), B500 results (`e3f5d016667d8db939b614055334fb50442d4899`). Stage 1 не запускает модели, обучение или CUDA. B-6000 не использовался.

## Реализация

- `kind=horizon` — правило существующей пользовательской категории; IDs, словари, Regex, TF-IDF, SetFit и RuBERT сохранены. Ни одной новой категории.
- Категорийный ANY/ALL переиспользует `evaluate_groups`, отдельно по телу и каждому вложению. Никаких новых политик/инцидентов. В ML runtime больше нет замещения TF-IDF специализированной моделью; публикация SetFit не отключает RuBERT.
- `horizon.infer` использует существующую neural-очередь, WorkItem, fencing token, immutable Content и снимок конфигурации. Остальной inference/политики продолжаются независимо; перед optional inference уже ставится policy evaluation.
- Параллельные optional результаты объединяются только для одинаковых extraction generation, текстов и снимков. Новое извлечение делает старые задания superseded; повторные задания не создают второй инцидент (существующий OneToOne message/Incident и idempotency).
- Ошибки/нет модели/исчерпание лимитов записываются в engine_errors/skipped_checks и PARTIAL. Терминальный сбой worker также фиксируется. При остановленном worker базовые политики не ждут его.
- Настройки в существующих формах категории: положительные/исключающие гипотезы, combine, aggregation, threshold, risk, enabled. Изменения сохраняются как CategoryRule; снимок + SHA256 конфигурации + timestamp версии фиксируются в evidence.
- PR38 FP32 конфигурации всех 12 категорий поставляются в `app/horizon_defaults.json`; явная команда установки создаёт только выключенные правила внутри уже существующих категорий, без перезаписи. Команда не запускалась на рабочем развёртывании.
- Карточка группирует методы по существующей категории, сохраняет все исходные находки и исторические параметры. Horizon показывает score, threshold, оценки/полярность выбранных гипотез, окно, источник, model ID, SHA256 весов и config. Гипотезные оценки показаны для лучшего окна; итоговый score использует заданную агрегацию.
- Оценки моделей не складываются/усредняются. Риск остаётся существующим max базовых рисков, а не растёт с количеством подтверждений. Horizon не увеличивает occurrence count, если эта категория уже найдена в том же документе; исходное число независимых legacy-вхождений сохраняется.
- Readiness в детекторах отличает configured, deployment gate, worker и последнее успешное задание. Наличие конфигурации не объявляется исправной моделью.

## Ограничения ресурсов и офлайн

Локальная модель загружается только в worker через local_files_only=True, trust_remote_code=False, safetensors. Нет API-клиента и загрузок из сети. CPU FP32 по умолчанию; CUDA только явным MICE_HORIZON_DEVICE=cuda, недоступность даёт неполный результат без отключения других методов. Обязательного GPU нет.
Окно 900 символов, overlap 100; tokenizer limit 512 и truncation=only_first. До 10 гипотез на правило по 600 символов; до 40000 символов на документ, 50 окон и 6000 пар на письмо, batch 8, CPU threads 2 (1–4). Ограничения и ошибки явные. Один cached encoder на процесс; pair cache только на время документа. Prefork hard/soft timeout и memory recycle переиспользуются из neural-worker.
Длинные письма/вложения обрабатываются раздельно, без склейки контекста разных MIME-источников. Обрезанные проверки PARTIAL; даже при наличии положительного evidence полнота не гарантируется. Естественные длинные письма отсутствовали в PR38 — агрегация окон пока не калибрована.

## Оставшиеся ограничения / перед эксплуатацией

1. Новый независимый, человечески проверенный корпус: длинные вложения, цитаты/новости, смешанный контент и обфускация. Не перенастраивать по B-500.
2. Только отдельное одобрение shadow rollout. Horizon глобально и seeded-правила выключены по умолчанию; никаких автоматических изменений deployment.
3. Наблюдение memory/latency и hard-kill/OOM на реальном worker/container. Зафиксированный CPU smoke не заменяет нагрузочный тест.
4. Readiness — последнее наблюдение, не online probe модели; HTTP не импортирует torch и не загружает веса.
5. В legacy API `custom_findings(session,...)` уже присутствовал неопределённый rules_for; Django использует evaluate_groups. Не мигрировать обратно на этот неиспользуемый legacy entrypoint.
6. Все сохранённые predictions/метрики остаются исследовательскими; автоматический выбор рекомендации в production НЕ реализован.
